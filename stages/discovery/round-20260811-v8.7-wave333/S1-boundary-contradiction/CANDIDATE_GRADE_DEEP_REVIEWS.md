# CANDIDATE_GRADE_DEEP_REVIEWS

## D01 — LMDB meta-page publication

- **Native legality witness.** On the same logical write set, action A writes newly allocated copy-on-write tree pages then updates the older meta page with the next transaction ID/root; action B is a failed/aborted transaction that leaves the older committed meta page selected. A reader uses the valid meta page with the highest transaction ID. Both actions are native and recovery-observable.
- **Current union closure.** Current official `mdb.c` pins page copy-on-write, transaction commit, two meta-page handling, map/sync modes and reader state. The current OpenLDAP backend documentation identifies LMDB as the official backend context. Sync flags/configuration are included in the baseline rather than used to assert an absence.
- **Primary collision.** The ATC 2020 fsync-failure study describes exactly the new-pages → fsync → metadata-page/root/transaction-ID update protocol and its error behavior. OSDI 2014 separately identifies LMDB's final pointer update as the shadow-paging commit requirement. These are direct semantic subtractors for a claimed “commit-point discovery”.
- **N1/N2 red team.** A `Meta-Page Pareto Planner` can only choose the stock next meta page/root publication versus abort. There is no independent legal action set: changing the reader selection rule or meta format changes the object; choosing delayed sync is configuration; optimizing tree page allocation is generic B-tree/allocator work and must preserve the same forced publication. No LMDB-specific new recurrence or guarantee survives.
- **Finite Stage A killer (not executed).** For a bounded upstream key/value trace, use two crash cuts around the meta-page update and verify stock reopen selects exactly the intended committed ID/root. Kill the preclaim if candidate output is stock page/meta ordering, selects an older/newer snapshot incorrectly, or relies on a changed sync/format contract. Charge CPU/RSS, write/sync count, bytes, p50/p90 commit and reopen time.
- **Decision:** `DROP` — the whole commit/recovery action union and direct semantics are already explicit.

## D02 — MySQL binlog ordered group commit

- **Native legality witness.** Two same-SQL traces can use a batch leader/participant group path or a non-batched/synchronous group boundary, while retaining required commit/binlog ordering. The current implementation assigns ordered stages rather than exposing arbitrary commit permutation.
- **Current union closure.** Current MySQL 8.4 binary-log manual and `sql/binlog.cc` pin the logging interface and ordered commit code; current binary-log/replica variables are part of the union. The source's group commit sequencing and storage-engine handoff make the visibility/recovery boundary explicit.
- **Primary collision.** FAST 2022's MyRocks passive logging work directly analyzes MySQL server-layer commit order, binlog semantic completeness and recovery constraints. It changes the storage/logging design; it does not leave a same-object algorithm that can reorder commits while retaining binlog/SQL recovery order.
- **N1/N2 red team.** Choosing group size, wait delay, flush cadence or leader timing is a controller/configuration problem. A generic batching scheduler is non-admissible. Permuting transactions across their source-pinned ordered stages changes binary-log/replica/recovery semantics. No target-specific exact/FPT/Pareto/approximation guarantee survives current union plus MyRocks collision.
- **Finite Stage A killer (not executed).** On bounded MTR transactional/binlog fixtures, enumerate a group leader/participant and a singleton path; verify SQL rows, binlog order and restart/replica result. Kill if candidate only picks current group delay/flush settings, changes binlog order, or is reproduced by stock ordered commit. Charge CPU/RSS, binlog bytes, syncs, group/commit latency and recovery time.
- **Decision:** `DROP` — native ordered group commit already owns the legal action set; residual is controller/tuning.
