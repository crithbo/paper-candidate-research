# CANDIDATE_GRADE_DEEP_REVIEWS

## D1 — Android DEX layout stability: `NOT_ADMITTED_UNFROZEN`

- **Exact object / oracle.** A fixed `classes.dex` logical class/method/code/annotation graph accepted by the stock ART `DexFile` reader and resolving the same symbols and bytecode. The AOSP DEX specification defines indexed and offset-addressed sections; legality must be checked by stock parsing plus a semantic symbol/code comparison, not byte equality.
- **Natural chain and proposed N2/N3.** Pin 20–50 small official AOSP APK/DEX build artifacts from adjacent tags, their SHA-256s and build fingerprints. Test a predeclared repeated-transition law: whether stable method/type/string identities preserve a bounded successor locality across held-out transitions. If it holds, the candidate action is a predecessor-aware bounded-window DP that jointly chooses legal ID order, class-data order and repaired offsets, with an explicit Pareto objective on final DEX bytes, VCDIFF bytes and stock read/start cost. This is a proposed target-specific N2; N3 is conditional on the held-out law. It is not a reorder flag or cache.
- **Current-upstream reality check.** Official DEX documentation confirms structured ID/data areas and LEB128 offsets. Current upstream must be pinned at the Stage-A start in `platform/art` (`dexlayout/` and dex-file reader/writer paths) together with `dex2oat`/`dexlayout` command options and all default/nondefault layout, compact-dex and verification settings. The present Discovery check found format legality, but did not close the complete source/config action union or establish that a stock tool cannot already reproduce the whole constructor. Counterevidence to preserve: dexlayout itself is a native layout tool and ART compilation can transform dex representations.
- **Strongest fair union.** Current per-version D8/R8/AOSP writer plus all legal dexlayout/dex2oat layout/verification modes, crossed with a same-information VCDIFF/binary-delta baseline. Both see the preceding DEX and the current logical graph.
- **Full cost and 72h killer.** Charge writer CPU, peak RSS/temp, final DEX bytes, patch bytes, stock DexFile load/verification/start CPU/RSS. Within 72h, first enumerate all current layout flags and produce two tiny format-valid, stock-reader-equivalent placements; **STOP/UNFROZEN condition:** if semantics includes order/checksum observables or the union already expresses the DP action, do not propose. This is finite, but not yet performed.
- **Decision.** `NOT_ADMITTED_UNFROZEN`: no brief. Structural paper potential cannot be rated honestly before the union and natural repeated-transition law are frozen. Current evidence readiness: low, because this is source and corpus closure work—not a resource or implementation failure.

## D2 — Rust `.rmeta` metadata placement: `NOT_ADMITTED_UNFROZEN`

- **Exact object / oracle.** A fixed crate metadata graph consumed by the *same pinned* rustc metadata decoder, preserving compiler resolution/type checking behavior. The current official rustc API documentation describes versioned `METADATA_HEADER`/`METADATA_VERSION`, lazy arrays/tables and `encode_metadata`; it does not promise an independently stable external `.rmeta` format.
- **Natural chain and proposed N2/N3.** Pin 20–50 official rustc tags and a fixed set of compiler-test crate inputs. The candidate would be a version-aware DP that assigns stable `LazyTable`/value positions using predecessor information while preserving the current tag’s decoder and metadata version, optimizing rmeta bytes plus VCDIFF delta bytes. A stable re-use law across held-out tags is prerequisite N3 evidence; the joint DP is the only possible N2.
- **Current-upstream reality check.** Official rustc docs name `METADATA_VERSION` and explicitly identify `rmeta::encoder`, `decoder`, `LazyTable`, `LazyArray` and `encode_and_write_metadata`; output is selected by `--emit=metadata`, with `-C extra-filename`, `--out-dir`, and output-path choices. Current `compiler/rustc_metadata` source/tag, all metadata-affecting `-C/-Z` options, incremental and crate-hash inputs still need an exact source pin before an absence/action claim. Counterevidence: the existing encoder already owns table building and lazy layout; a generic placement claim may be absorbed.
- **Strongest fair union.** The pinned tag’s complete rustc metadata encoder/configuration plus the same predecessor artifact and a standard VCDIFF/binary-delta baseline. No cross-rustc reader guarantee may be assumed.
- **Full cost and 72h killer.** Charge compiler/metadata writer CPU, peak RSS/temp, rmeta bytes, delta bytes, and downstream metadata-load/type-check CPU/RSS. Killer: show two same-tag decoder-equivalent metadata layouts on a minimal official compiler test, then exhaust source options; **STOP/UNFROZEN:** if internal offsets are not independently constructible or current encoder absorbs the action. No run occurred.
- **Decision.** `NOT_ADMITTED_UNFROZEN`: external semantics and current union are not sufficiently frozen. This is not a claim that no natural stability exists and not a readiness-based rejection.

## D3 — CPython hash-based `.pyc`: `STRUCTURAL_DROP`

- **Exact object / oracle.** Fixed source hash, interpreter magic, import result and code-object behavior under stock importlib. Official documentation states bytecode is an optimization with no bytecode-specific API, and exposes invalidation choices (`TIMESTAMP`, `CHECKED_HASH`, `UNCHECKED_HASH`) rather than a layout-construction interface.
- **Current union / counterevidence.** `py_compile` and importlib are the current producer/reader union; `--check-hash-based-pycs` changes cache validation, not a legal semantic placement action. Any marshal-level rewrite either needs a non-stock reader or changes bytecode/code-object references beyond the stated stock contract.
- **Decision.** `STRUCTURAL_DROP__NO_WHOLE_STOCK_SEMANTIC_CONSTRUCTOR`; a version-aware external delta or cache layer is expressly out of scope.
