# CANDIDATE_GRADE_DEEP_REVIEWS

## D01 — SQLite WAL visibility/checkpoint construction

- Exact object and guarantee: one WAL-mode SQLite database; identical committed SQL state, atomicity, per-reader snapshot end-mark, and stated `PRAGMA synchronous` durability contract. A checkpoint is not allowed to invalidate a reader's end-mark.
- Current reality / strongest union: official WAL documentation pins COMMIT to appending its commit record; readers retain their end mark; checkpoint stops before a reader's end mark and resumes later. The documented union includes automatic checkpoint at the configured threshold, disabling/deferment, user callback and PASSIVE/FULL/RESTART checkpoint entrypoints. Source location: `src/wal.c`, official Fossil trunk URL; relevant default is `SQLITE_DEFAULT_WAL_AUTOCHECKPOINT` (1000 pages unless compiled otherwise); the public APIs are the non-default action entrance.
- Minimal legal divergence witness: with reader A fixed before commit k+1, an auto-checkpoint triggered by the writer may do partial work whereas a later FULL/RESTART request chooses a blocking/completing path. Both retain A's snapshot semantics. This is a divergence of checkpoint *policy*, not a new same-information atomic constructor.
- Direct subtractors/collision: SQLite's own documented PASSIVE/FULL/RESTART and auto/manual checkpoint union; TxFS and WALDIO change filesystem or durability-layer assumptions rather than give a same-object native SQLite constructor.
- Six-dimensional test: decision rule is documented policy selection; information adds no target-specific state beyond existing locks/end marks; cost is a familiar read/write/checkpoint tradeoff; guarantee is already parameterized by checkpoint mode; all fsync/reader blocking costs are documented; a no-gain boundary is exactly long-lived-reader starvation. Hence a claimed optimizer is a controller/policy, not N2.
- Natural route/full cost: public SQL traces; stock `integrity_check`, reopen recovery, WAL checkpoint results; compile CPU/RSS, SQL latency, WAL bytes, fsyncs, blocked-reader time and recovery time. 72h killer: one bounded trace set with long-reader, short-reader and write bursts; stop preclaim if every candidate action is reproduced by stock checkpoint APIs or changes snapshot/durability semantics.
- Decision: `DROP` — current union absorbs the whole legal action space; no non-generic target-specific algorithm/guarantee remains. This is not a readiness inference.

## D02 — PostgreSQL 2PC prepared-state/checkpoint handoff

- Exact object and guarantee: a fixed PostgreSQL distributed 2PC transaction graph with the same SQL effects, XA-style prepared state, crash recovery and COMMIT/ROLLBACK PREPARED semantics.
- Current reality / strongest union: current PostgreSQL documentation says 2PC exposes PREPARE, COMMIT PREPARED and ROLLBACK PREPARED; while short-lived state is in shared memory/WAL, transactions spanning a checkpoint are recorded in `pg_twophase`. WAL must be flushed before data changes and serves REDO recovery. Source pin targets are official PostgreSQL `src/backend/access/transam/twophase.c` and WAL code path at the current 2026-08-11 upstream branch; non-default knobs and external transaction-manager timing are not treated as an absence claim.
- Minimal legal divergence witness: a prepared xact immediately before versus after a checkpoint changes its persistence carrier, while only the two terminal protocol actions remain legal. Any alternative that delays/chooses the terminal action is an external transaction-manager/retry policy; any reordering that exposes it changes the frozen recovery/visibility contract.
- Direct subtractors/collision: stock 2PC recovery path and WAL group-commit behavior. The original WAL contract already permits shared WAL flush amortization; external-XA scheduling is explicitly outside a PostgreSQL-native same-information constructor.
- Six-dimensional test: no additional native decision information; the only apparent action is terminal-transition timing; its resource effect is external coordination, its guarantee boundary is fixed, and no separate full-cost denominator removes this dependency. No target-specific recurrence/approximation claim survives.
- Natural route/full cost: PostgreSQL regression prepared-xact tests and crash/restart fixtures; SQL/catalog oracle; CPU/RSS, WAL/`pg_twophase` bytes, flushes, commit latency, restart/recovery time. 72h killer: enumerate prepared xacts across a checkpoint and show whether a proposed action either matches stock state transitions or breaks COMMIT/ROLLBACK/recovery equivalence.
- Decision: `DROP` — same-object residual reduces to a controller/retry policy or changed recovery semantics.

## D03 — LLVM ORCv2 materialization/resource-removal seam

- Exact object and guarantee: fixed ORCv2 JITDylib, symbol lookup results and the promise that code/data are not released until dependencies are safe to call or use; removal/failure must not publish removed materialization.
- Current reality / strongest union: ORCv2 documents concurrent lookup/materialization, dependency tracking, `MaterializationResponsibility`, and explicit `ResourceTracker` removal/transfer. Current source locations are `llvm/lib/ExecutionEngine/Orc/Core.cpp`, `llvm/include/llvm/ExecutionEngine/Orc/*`, and `llvm/unittests/ExecutionEngine/Orc/ResourceTrackerTest.cpp`; the standard union includes default tracker and explicit tracker actions, not merely a default flag.
- Minimal legal divergence witness: an in-flight unit and a removal request race. Native semantics force the materializer to receive an error before it can update JIT state; a transfer associates ongoing/future resources with the destination key. Both paths are already named stock actions.
- Direct subtractors/collision: LLVM's ResourceTracker API and ObjectLinkingLayer failure/removal/transfer callbacks, plus ORCv2's documented dependency guarantees. The public API makes ownership transition an explicit composable primitive.
- Six-dimensional test: a proposed batching/scheduling rule selects only existing remove/transfer/lookup actions; it has no additional target-specific information/legality; a generic state graph schedules callbacks; any postponement changes client-visible removal/lookup timing. It therefore fails N2 even though the witness is real.
- Natural route/full cost: LLVM ORC unit tests and removable-code examples; JIT lookup/error/resource lifetime oracle; compile CPU/RSS, code/data bytes, materialization latency, removal latency, runtime memory. 72h killer: run the native unit fixture (Stage A only) under an in-flight materialization/remove witness; stop preclaim if stock error/transfer handlers implement all candidate transitions.
- Decision: `DROP` — strongest current union explicitly absorbs the ownership-transition space.
