# Paper Candidate Research Pipeline

> 一个面向计算机系统、编译器与体系结构研究的证据驱动论文课题筛选项目。

本项目把“找到值得投入的论文题目”从一次性的灵感判断，转化为可复核、可停止、可交接的研究流水线。它从公开论文、官方文档、上游源码、规范与基准中发现机会；冻结研究对象和候选主张；检查最新工作是否已经覆盖核心机制；定义公平强基线、完整成本和可证伪条件；再通过独立阶段门决定是否继续投入实现与实验。

公开版本保留了真实的课题筛选案例、方法规则、标准模板、阶段交接与最小证据。一个仍需保密的候选已从公开快照与已发布 Git 历史中移除。

为了让公开仓库更适合复核和简历展示，快照不包含内部控制面状态、本机运维日志、大型哈希清单和下载的论文 PDF。保留的内容聚焦于研究方法、可复用合同、候选案例和评审证据。

## 为什么做这个项目

论文选题常见的问题不是“没有想法”，而是没有及早回答这些问题：

- 候选方法和基线是否解决同一个对象、同一种语义和同一组约束；
- 最新论文、官方文档或当前源码是否已经实现了核心动作；
- 比较器是否足够强，预算、输入与信息条件是否公平；
- 性能或质量收益是否计入编译、转换、内存、调优和运行时等完整成本；
- 是否存在一个便宜、明确、能够推翻核心假设的实验；
- 结论是否能由公开输入、固定版本和可复现步骤支持。

本仓库用结构化合同、角色隔离、阶段门和证据台账，把这些问题前置到高成本实现之前。得到“停止”结论也是有效产出：它能避免在已被覆盖、对象不一致或无法公平验证的方向上继续投入。

## 流水线概览

```text
Discovery → Stage 0 → Stage A → 人工复核 → Stage B → 独立复审 → 正式论文项目
```

| 阶段 | 核心问题 | 主要输出 |
|---|---|---|
| Discovery | 能否从公开证据形成清楚、有限、可证伪的研究问题？ | Topic Brief、来源日志、候选 handoff |
| Stage 0 | 新颖性、同对象关系、最新碰撞和论文结构是否成立？ | 碰撞审查、比较器矩阵、继续/停止建议 |
| Stage A | 最关键的机制前提能否在小规模、真实构造上成立？ | 环境锁、运行索引、初步证据、成本账本 |
| Human Gate | 是否值得授权更高成本的 Stage B 工作？ | 用户审查包、资源与范围批准 |
| Stage B | 主要证据链、完整成本、边界与复现是否闭合？ | Claim–Evidence Matrix、阶段报告、复现包 |
| Independent Review | 未参与实现的审查者能否复核同一结论？ | 独立审查报告与最终缺口 |
| Formal Project | 是否具备论文写作、引用审计和发布准备条件？ | 稿件计划、复现包、投稿检查清单 |

阶段门不按数量晋级，也不以模型自评分替代证据。每个阶段都允许诚实停止、暂存或返回修订。

## 核心设计原则

### 1. 先冻结主张，再观察结果

每个候选都要写清 `exact object`、动作或机制、目标指标、保证、输入条件、信息条件和 full-cost 边界。结果出现后不能通过更换对象、降低保证或缩小分母来“挽救”主张。

### 2. Same-object 公平比较

候选方法与基线必须处理相同对象、相同语义和相同约束。把更容易的问题与更难的问题比较，或者遗漏基线必须支付的同类成本，不能构成论文贡献。

### 3. 当前碰撞优先

新颖性审查不只看论文标题，还检查官方文档、当前上游源码、默认/非默认特性、版本与配置入口。旧版文档中的“缺失功能”不能自动证明当前仍有研究空白。

### 4. 完整成本核算

端到端结论需要计入可能改变决策的成本，例如编译时间、调优预算、数据转换、物化、峰值内存、缓存、设备占用和运行时开销。

### 5. 可证伪，而非只可展示

每个候选都定义最小 killer test。如果已有实现覆盖核心动作，公平基线复现全部收益，或者自然输入中没有剩余空间，该题应立即收缩或停止。

### 6. 角色与证据隔离

候选执行者不能独立批准自己的结果；Stage A/B 使用不同审查角色。共享状态只允许控制面单写，避免多个代理并发改写同一事实源。

### 7. AI 执行性与学术价值分离

自动化能力用于安排检索、实现、重放和审计，不替代研究判断。AI 是否方便执行不会改变新颖性、证据质量或论文等级。

## 仓库中的主要资产

```text
.
├── .agents/skills/       # 可复用的研究发现与执行 runbook
├── .github/workflows/    # 仓库安全检查
├── docs/                 # 分支与执行说明
├── rules/                # 角色权限、阶段门和资源/生命周期规则
├── scripts/              # 自动化校验脚本
├── stages/
│   ├── discovery/        # 发现批次、来源日志和候选 brief
│   ├── stage0/           # 新颖性与论文结构审查
│   ├── stageA/           # 受限的机制验证与独立 gate
│   └── stageB/           # 高成本证据闭环（需人工逐题批准）
├── templates/            # 报告、合同、台账、复现与审查模板
└── AGENTS.md             # 项目目标、权限和全局硬门
```

`stages/` 中的案例展示了不同结论：继续、修订、阻塞、保留或停止。它们是研究过程记录，不应被理解为都已形成论文结论。

日常运行时的 `plan.md`、`registry.yaml`、`history.md` 与 `stages/control/` 属于内部控制面，不是课题案例的必要组成部分，因此没有收录在公开快照中。

## 数据合同与可追溯性

仓库使用 Markdown 记录人可读的研究判断，使用 YAML 固定机器可读边界。典型合同包括：

- [`templates/DISCOVERY_QUESTION_CARD.md`](templates/DISCOVERY_QUESTION_CARD.md)：研究问题、对象、证据路线与 closure debt；
- [`templates/TOPIC_BRIEF.md`](templates/TOPIC_BRIEF.md)：候选主张、机制、基线、full-cost 与 falsifier；
- [`templates/ASSIGNMENT_CONTEXT.yaml`](templates/ASSIGNMENT_CONTEXT.yaml)：角色、写目录、规则版本、允许和禁止动作；
- [`templates/ENVIRONMENT_LOCK.yaml`](templates/ENVIRONMENT_LOCK.yaml)：工具链、平台和输入身份；
- [`templates/RUN_INDEX.yaml`](templates/RUN_INDEX.yaml)：运行状态、有效性与对应证据；
- [`templates/CLAIM_EVIDENCE_MATRIX.yaml`](templates/CLAIM_EVIDENCE_MATRIX.yaml)：主张与证据的对应关系；
- [`templates/INDEPENDENT_REVIEW_REPORT.md`](templates/INDEPENDENT_REVIEW_REPORT.md)：独立复核与未闭合风险；
- [`templates/REPRODUCIBILITY_PACKAGE.yaml`](templates/REPRODUCIBILITY_PACKAGE.yaml)：复现入口、版本、输入和结果边界。

这些模板不是为了制造文档数量，而是防止对象、基线、分母和证据在多轮代理协作中漂移。

## 如何阅读案例

建议按以下顺序阅读一个候选：

1. 从 `stages/discovery/` 的 Topic Brief 了解研究问题、机制假设和初始来源；
2. 查看对应 Stage 0 报告，确认最新碰撞、同对象关系和 Q1/Q2 论文结构判断；
3. 如果进入 Stage A，检查环境锁、执行合同、关键 observation 和独立 gate；
4. 对照 `handoff.yaml` 与 manifest，确认上游主张没有被下游改写；
5. 重点看 falsifier、负结果、full-cost 和 evidence ceiling，而不只看最终状态。

## 如何复用这套方法

### 1. 创建研究问题

阅读 [research-topic-discovery skill](.agents/skills/research-topic-discovery/SKILL.md)，选择一个精确的公开 anchor，并用 Discovery Question Card 固定问题、来源角色和停止条件。

### 2. 形成候选 brief

复制 `templates/TOPIC_BRIEF.md`，至少完成 exact object、主要 claim、strongest fair baseline、当前碰撞、机制假设、decisive falsifier、full-cost 和有限证据路线。

### 3. 分阶段验证

先完成便宜且信息增益最高的检查。Stage A 只验证关键前提，不把小规模正结果写成完整论文主张；Stage B 需要逐题人工批准后再启动。

### 4. 保留可复现边界

固定依赖、版本、输入、命令、预算与无效运行。大型源码、模型、数据、工具链、构建目录和缓存不进入 Git；仓库只保留 provenance、哈希、最小 fixture 和决定性证据。

## 仓库安全检查

运行：

```bash
python scripts/check_repository_snapshot.py
```

同一检查会由 GitHub Actions 在推送和 Pull Request 时执行。它会拒绝常见资源目录、构建产物、缓存、归档、二进制文件和超过 50 MiB 的已跟踪文件，降低误提交本地环境或大型实验资源的风险。

## 技术实现

- Markdown：人可读的研究合同、报告与审查材料；
- YAML：机器可读的状态、交接、环境、运行和证据索引；
- Python：仓库快照与边界检查；
- Git / GitHub Actions：版本化、分支隔离与持续完整性检查；
- Codex Skills：把研究发现和阶段执行编码为可复用的代理 runbook。

## 项目展示点

这个仓库主要展示：

- 将开放式研究选题转化为可审计状态机的能力；
- 把文献检索、源码核验、实验设计和独立审查连接为同一证据链；
- 用权限边界、数据合同和自动检查控制多代理研究工作流中的状态漂移；
- 对失败、未知、资源阻塞和证据上限进行显式建模，而不是只保留正结果；
- 在公开源码、公开数据和有限本地算力条件下规划可复现的系统研究。

## 边界与免责声明

- 本仓库是研究方法与候选审查项目，不等同于已发表论文集合。
- 阶段 PASS 只表示相应阶段的条件得到支持，不代表完整主张已经成立。
- 案例中的评分、状态和方向判断来自特定时间截面的公开证据，可能随上游演进而失效。
- 对第三方项目、论文、规范和文档的引用仅用于研究背景；版权与许可证归原作者所有。
- 仓库未附带开源许可证；除 GitHub 平台允许的浏览和分叉外，不自动授予复制、修改或再发布权利。

## 公开版本说明

公开版本保留可审计的研究案例和流水线方法。一个仍在保密范围内的候选及其路径、内容和历史引用已被排除；本机凭据、私密输入、下载资源和构建产物不属于公开仓库。
